# Audit — 2026-06-12

Second full-stack audit, post-remediation of [audit-improvements.md](audit-improvements.md) (all 16 items from 2026-06-07 closed except yjsState pruning). Scope: NestJS server, `sync-engine` package, Expo mobile app, workspace config.

**Verdict:** the architecture is sound and the previous audit's fixes are real — true-delta fan-out, subprotocol auth, origin-tagged propagation, env validation, and rate limiting all verified in source. Remaining findings are one dependency-hygiene bug, a connection-lifecycle gap, and scale-horizon items that are acceptable for an MVP but should stay on the radar.

### 1. 🟠 `@expo/ui` is a phantom dependency

`apps/mobile/src/ui/index.ts` and `modifiers.ts` import from `@expo/ui` and its subpaths, but `@expo/ui` is absent from `apps/mobile/package.json`. It resolves only because `expo-router@56.2.9` depends on `@expo/ui@^56.0.16` and bun hoists it to the root `node_modules`.

Risk: any expo-router patch release can silently change the `@expo/ui` version the app compiles against, or a hoisting change can break resolution entirely. For a beta-API package this is the worst place to be implicit.

**Fix:** add `"@expo/ui": "~56.0.16"` to `apps/mobile/package.json` dependencies.

### 2. 🟡 No WS heartbeat — dead sockets linger

`SyncGateway` never pings clients. A half-open TCP connection (app killed, network drop without FIN) stays in `room.clients` with `readyState === OPEN` until the OS TCP timeout — potentially many minutes.

Impact is bounded: presence self-heals because the awareness protocol expires states after ~30 s, and `send()` checks `readyState`. But the dead socket blocks the 30 s room GC (`clients.size > 0`), keeps the room doc in memory, and receives every fan-out attempt.

**Fix:** standard `ws` ping/pong sweep — ping all clients every 30 s, `terminate()` any that missed the previous pong. `terminate()` fires `close`, so existing `handleDisconnect` cleanup (awareness removal, room GC) runs for free.

### 3. 🟡 `yjsState` unbounded growth — still open

Carried over from the previous audit (deliberately deferred). Yjs tombstones accumulate for the room's lifetime; both persistence tiers write the full encoded state, so write cost is O(history) per flush and grows forever. Single-room MVP makes this slow-burn, but it is the one structural scale ceiling in the design. See ADR 002/006 consequences.

**Path:** periodic snapshot — load doc, re-encode into a fresh doc (drops tombstones for a message list that is append-only), swap the blob. Needs a "no writers" window or version-check swap.

### 4. 🟡 `SyncGateway` has zero test coverage

Server tests: `auth.service.spec.ts` only. The gateway — auth handshake, membership gate, sync protocol, Redis origin-tagging, awareness cleanup, rate limiting, room GC — is the most complex and most security-sensitive file in the repo and is exercised only manually. The sync-engine package, by contrast, has unit tests for all three classes.

**Fix:** gateway tests with a fake `WebSocket` pair + ioredis-mock: token reject (4001), non-member reject (4003), delta fan-out excludes origin, Redis echo suppression, disconnect clears awareness.

### 5. 🟡 TypeScript version skew

Root pins `typescript ^5.8.0`; `apps/mobile` pins `~6.0.3`. Two compiler majors in one workspace means lint/build behavior differs per package and editor tooling picks one arbitrarily.

**Fix:** align on one version at the root, remove per-package pins (or pin identically everywhere).

### 6. 🟢 Base64-in-TEXT persistence

`IStorage` is string-only, so `SQLitePersistence` base64-encodes (~33% size overhead + encode CPU on JS thread). Fine at chat-message volume; if profiling ever shows it, extend `IStorage` with a bytes variant and store BLOB. Deliberate trade-off — see ADR 005.

### 7. 🟢 No backpressure guard on fan-out

`room.clients.forEach(... client.send(msg))` never checks `bufferedAmount`. One slow consumer on a busy room buffers unboundedly server-side. At current message sizes (64 KiB frame cap, 60 msg/s rate cap) the bound is effectively ~4 MB/s per slow client — acceptable, but add a `bufferedAmount` threshold-kick if rooms grow.

### 8. 🟢 Redundant multi-instance persists

Every instance that has a room loaded debounce-persists the full state on updates it originates. With N instances, up to N writers race on `Room.yjsState`. Benign — all docs converge via Redis so last-writer-wins loses nothing — but it is wasted IO and a subtle invariant ("benign because converged") that a future change could break. Option: single-persister election via `SET NX` Redis lock per room.

## What is healthy (verified, not assumed)

- **True-delta propagation** — doc `update` handler is the single fan-out point; Redis carries real increments, origin tags (`client` / `'redis'` / `instanceId`) prevent echo loops in both directions.
- **Auth before resources** — JWT verified and membership checked before the room doc is touched; distinct close codes (4001/4003/4029/1009) let the client distinguish "re-auth" from "retry".
- **Offline correctness does not depend on the in-memory queue** — `pendingUpdates` is an optimization; the sync-protocol state-vector handshake on reconnect is the correctness mechanism, and SQLite survives process death.
- **`yjs` as peerDependency** in sync-engine — prevents the dual-Yjs-instance bug (identity checks break across copies).
- **Fail-fast env** — zod schema refuses boot on missing/weak `JWT_SECRET`.
- **Lifecycle discipline** — debounced persists flushed on destroy/GC, awareness cleared on disconnect, room init race guarded by promise map.

## Suggested order

1. #1 — one-line fix, real risk.
2. #2 + #4 together — heartbeat is most testable alongside new gateway tests.
3. #5 — config-only.
4. #3 — design the snapshot strategy before the blob is big enough to hurt (ADR candidate).
5. #6–#8 — revisit at multi-room / scale milestone.
